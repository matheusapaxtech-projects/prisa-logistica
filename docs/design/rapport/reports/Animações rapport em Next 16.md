# Três motores de animação recriam o rapport

Dá para reproduzir o rapport no Next.js 16.4 + React 19.2 + Tailwind v4 sem nenhuma biblioteca de transição de página, desde que o trabalho seja dividido entre três motores. O `<ViewTransition>` nativo do React cuida da troca de rota. O **Motion 14.6** (`motion/react`) cuida de tudo que acontece dentro da página: pílula que desliza, números com mola, metamorfose do gráfico, cartão que vira ficha e reacomodação do quadro. O CSS puro cuida do fundo, do vidro, da cascata de entrada e das trocas de cor. O ponto que mais pesa na decisão é o Quadro da operação. O arraste nativo do HTML5 que o app usa hoje entrega o destaque da coluna, a reacomodação e a volta animada quando o servidor recusa. Ele **não consegue** entregar o cartão "levantado" que escala e gira seguindo o ponteiro, porque o navegador congela a imagem do arraste no `dragstart`. Só uma biblioteca baseada em pointer events entrega isso, e hoje a candidata é a `@dnd-kit/react` 0.5.1, que ainda é pré-1.0. Por isso a recomendação é migrar em duas fases: primeiro Motion + `useOptimistic` em cima do arraste nativo, depois um spike com dnd-kit só para o levantamento. Duas descobertas mudam o desenho. `backdrop-filter` sobre um gradiente suave quase não aparece na tela, então o vidro fica reservado para o que flutua sobre conteúdo de verdade. E `prefers-reduced-motion` precisa de três interruptores diferentes, porque nenhum dos motores cobre os outros.

## Cada animação do rapport tem um dono diferente

A divisão sai das limitações de cada ferramenta. No App Router, o Next desmonta a rota antiga quase na hora, e por isso o `AnimatePresence` do Motion nunca roda a animação de saída. O contorno conhecido, o "FrozenRouter", congela o `LayoutRouterContext` interno, que **ainda é exportado no 16.4.2** mas não tem documentação e "pode quebrar a qualquer momento" ([LogRocket](https://blog.logrocket.com/advanced-page-transitions-next-js-framer-motion); [unpkg next@16.4.2](https://unpkg.com/next@16.4.2/dist/shared/lib/app-router-context.shared-runtime.d.ts)). Já o guia atual do Next (atualizado em 15/10/2026) diz que as view transitions "funcionam no App Router sem configuração". A antiga flag `experimental.viewTransition` foi removida, e a página dela agora retorna 404 ([Next.js view transitions](https://nextjs.org/docs/app/guides/view-transitions)). O `<ViewTransition>` ficou **estável no React 19.3**, publicado em 9/9/2026 ([React 19.3](https://react.dev/blog/2026/09/09/react-19-3)), e o `next@16.4.2` já embute um React `19.3.0-canary` para o App Router ([unpkg next@16.4.2](https://unpkg.com/next@16.4.2/dist/compiled/react/cjs/react.production.js)). Então o import funciona mesmo com `react@19.2.4` no `package.json`. A diferença de versão aparece nos tipos: o `@types/react` 19.2 pode não declarar `ViewTransition`.

| # | Animação do rapport | Motor | Técnica central |
|---|---|---|---|
| 1 | Página desfocado→nítido em cascata | `<ViewTransition>` + CSS | saída curta com blur 3px; blocos com `@keyframes` e atraso por índice |
| 2 | Pílula de navegação que desliza | Motion | `layoutId` dentro de `LayoutGroup id={useId()}` |
| 3 | Números que contam com mola | Motion | `useSpring` → `useTransform` → `motion.span`, sem re-render |
| 4 | Linha que se desenha e se transforma | CSS + Motion + d3 | `pathLength={1}` + `stroke-dashoffset`; `d3-interpolate-path` movido por `animate()` |
| 5 | Kanban: levanta e reacomoda | dnd-kit (fase 2) + Motion | levantamento no invólucro interno; `layoutId` por cartão; `useOptimistic` |
| 6 | Cartão que vira modal | Motion | mesmo `layoutId` no cartão e na ficha, `AnimatePresence`, `borderRadius` via `style` |
| 7 | Diálogo com fundo desfocado | CSS + Motion | um único véu fixo com `backdrop-filter: blur(8–12px)`; anima só a opacidade |
| 8 | Toast pílula com Desfazer | Sonner | `unstyled` + `classNames`, `action` com ação compensatória |

Algumas restrições valem para todos os componentes Motion. A versão atual é a **14.6.0**, com peer React `^18 || ^19`. A API React não teve mudança incompatível da 12 à 14 ([npm motion](https://registry.npmjs.org/motion/latest); [guia de upgrade](https://motion.dev/docs/react-upgrade-guide)). O pacote `motion` embute uma versão exata de `framer-motion`, então só o `motion` deve ser instalado, para não carregar duas cópias e quebrar contextos compartilhados como `LayoutGroup` e `MotionConfig`. Tudo que usa Motion roda no cliente. A regra é manter páginas e layouts como Server Components e colocar a animação em folhas `"use client"` ([instalação Motion](https://motion.dev/docs/react-installation)). Dois relatos merecem atenção nesta máquina Windows. O primeiro: `motion@12.40` fez o dev server Turbopack do Next 16.2 estourar memória no Windows. O issue foi fechado sem dizer qual versão corrigiu ([#3741](https://github.com/motiondivision/motion/issues/3741)). O segundo: animações "presas no estado inicial" no Next 16 se resolveram apagando `node_modules`, o cache do npm e `.next` ([#3565](https://github.com/motiondivision/motion/issues/3565)). Se o React Compiler estiver ligado, ele memoiza o elemento e as animações de `layout` deixam de disparar. O mantenedor recomenda passar os itens em `layoutDependency` ([#3416](https://github.com/motiondivision/motion/issues/3416)).

## Trocar de página: o Next faz a saída, o CSS faz a cascata

O efeito A1 tem duas metades. A tela antiga desfoca e some, e a nova entra em cascata. A saída é exatamente o que o `<ViewTransition>` resolve. A receita oficial do Next tira o conteúdo antigo em **150 ms** e faz o novo entrar com fade de 210 ms atrasado em 150 ms, usando `filter: blur(3px)` nos keyframes, porque "o conteúdo antigo deve sair rápido" e o novo "chegar com mais calma" ([Next.js view transitions](https://nextjs.org/docs/app/guides/view-transitions)). O wrapper precisa ficar **em cada `page.tsx`, não no layout**, porque o layout persiste entre navegações e nele enter/exit nunca disparam. Ele também precisa ser o primeiro nó, antes de qualquer `<div>` ([react.dev ViewTransition](https://react.dev/reference/react/ViewTransition)).

O detalhe que mais importa neste app é o `default="none"`. Só Transitions (`startTransition`), revelações de `<Suspense>` e `useDeferredValue` ativam um `<ViewTransition>`, e com `default="none"` todos os outros gatilhos ficam desligados ([react.dev ViewTransition](https://react.dev/reference/react/ViewTransition)). O Quadro vai mover cartões dentro de `startTransition`, porque o `useOptimistic` exige isso. Sem `default="none"`, cada movimento e cada recarga em transição fariam o navegador tirar um snapshot da página e animar uma "atualização" por cima das animações de `layout` do Motion. Por isso a página declara só `enter` e `exit`:

```tsx
// app/(app)/quadro/page.tsx (Server Component)
import { ViewTransition } from "react"
export default async function Page() {
  return (
    <ViewTransition enter="entrar" exit="sair" default="none">
      {/* conteúdo */}
    </ViewTransition>
  )
}
```

```css
::view-transition-old(.sair) { animation: 150ms ease-out both vt-fade reverse; }
::view-transition-new(.entrar) { animation: 120ms ease-out both vt-opacidade; }
::view-transition { pointer-events: none; }
@keyframes vt-fade { from { opacity: 0; filter: blur(3px); } to { opacity: 1; filter: blur(0); } }
@keyframes vt-opacidade { from { opacity: 0; } }
```

A cascata não cabe no `<ViewTransition>`. O CSS não alcança `nth-child` dos pseudo-elementos de transição, e não existe receita oficial de stagger. Usar um `<ViewTransition>` por bloco com `onEnter` funciona, mas multiplica snapshots. O caminho mais barato é um keyframe do Tailwind v4 declarado no `@theme` (`--animate-surgir`) e aplicado com `motion-safe:animate-surgir`, com `animation-delay` calculado a partir de um índice inline ([Tailwind theme](https://tailwindcss.com/docs/theme)). Essa escolha tem uma vantagem sobre variants do Motion com `delayChildren: stagger(0.04)`: o CSS roda já no HTML do servidor, sem esperar a hidratação. Já um `initial="hidden"` do Motion deixa o bloco invisível até o JavaScript carregar, o que piora o primeiro carregamento. O Motion continua valendo para cascatas que dependem de estado do cliente, como a lista de clientes filtrada. Nesse caso a API atual é `delayChildren: stagger(...)`, porque `staggerChildren` está marcado `@deprecated` nos tipos da 14.6 ([unpkg motion-dom](https://unpkg.com/motion-dom@14.6.0/dist/index.d.ts)). Juntar a saída nativa com a cascata em CSS é uma inferência minha: nenhuma fonte documenta a combinação, e ela precisa de um teste no navegador. Os parâmetros do rapport (blur 8px, 350 ms, 40 ms por bloco) devem cair para **3–6px** no blur, valor que as próprias receitas do Next usam.

O suporte a view transitions no mesmo documento cobre Chrome/Edge 111+, Safari 18+ e Firefox 144+, cerca de **93% do uso global**. Sem suporte, a navegação acontece normalmente, só sem animação ([caniuse](https://caniuse.com/view-transitions)). A versão de transição de página com Motion mais uma `template.tsx` só faz entrada, porque o template remonta a cada navegação e por isso não tem saída. Ela fica como plano B caso o snapshot nativo dê problema no Safari, já que o próprio guia avisa que "algumas animações podem se comportar diferente" lá.

## Pílula, números, gráfico e ficha cabem no Motion

A pílula da navegação (A2) e os controles segmentados (A10) são o mesmo componente: um `motion.span` com `layoutId` fixo, renderizado só dentro do item ativo. Como o "`layoutId` é global no site", cada instância precisa de um `<LayoutGroup id={useId()}>` para que "6M/12M" e "Board/List" não compartilhem a pílula ([Motion LayoutGroup](https://motion.dev/docs/react-layout-group)). O raio vai em `style={{ borderRadius: 9999 }}`, e não em classe Tailwind, porque o Motion só corrige a distorção de raio e sombra quando eles vêm por `style` ou por props de animação ([Motion layout](https://motion.dev/docs/react-layout-animations)). A versão 14.6.0 corrigiu justamente "`layoutId` pulando" e `scale`/`x`/`y` aplicados em dobro no layout compartilhado ([changelog](https://motion.dev/changelog)), o que é motivo para fixar `^14.6`.

Os números (A3) usam `useSpring(0)`. Um `useTransform` deriva a string formatada em BRL, e essa MotionValue é renderizada como filho de um `motion.span`. O Motion escreve direto no DOM "sem disparar re-render do React" ([Motion motion values](https://motion.dev/docs/react-motion-value); [useSpring](https://motion.dev/docs/react-use-spring)). Três cuidados evitam bugs reais. O `Intl.NumberFormat` deve ser criado uma vez, fora do render. O `aria-label` deve levar o valor final, para o leitor de tela não ouvir os números intermediários. E o espaço depois de `R$` é **U+00A0**, o que quebra snapshots de teste que comparam com espaço comum (verificado em Node 24.14). O `tabular-nums` impede que os dígitos tremam de largura. O `AnimateNumber` pronto existe, mas é do Motion+, pago ([AnimateNumber](https://motion.dev/docs/react-animate-number)). Há uma troca a decidir no SSR: começar em 0 dá o efeito de contar na entrada, mas o HTML do servidor mostra "R$ 0,00" até a hidratação. Começar com `useSpring(valor)` mostra o número real e anima só nas trocas de período.

O gráfico (A4) é o único lugar onde o Motion sozinho não basta. O Motion anima o atributo `d` só quando os dois caminhos têm o mesmo número e tipo de comandos ([Motion SVG](https://motion.dev/docs/react-svg-animation)), e passar de 6 para 12 meses dobra os pontos. A ferramenta certa é `d3-interpolate-path` (2,5 kB gzip), que "estende os dois caminhos para terem o mesmo número de pontos". Para a área, `excludeSegment` evita que as bordas verticais "derretam" ([d3-interpolate-path](https://github.com/pbeshai/d3-interpolate-path)). Com `d3-shape` (`curveMonotoneX`, que não oscila entre pontos) e `d3-scale`, o pacote fica em torno de 25 kB gzip antes da árvore de dependências ser podada ([d3-shape curvas](https://d3js.org/d3-shape/curve); [bundlephobia d3-scale](https://bundlephobia.com/package/d3-scale@4.0.2)). O `animate(0, 1, { onUpdate })` do Motion move a interpolação e grava o `d` direto no elemento. Assim o React nunca é dono do atributo e não briga com a interpolação. O desenho inicial é independente disso: `pathLength={1}` no `<path>` mais um keyframe de `stroke-dashoffset` de 1 para 0. A alternativa pronta é o **Recharts 3.10.1**, que ganhou `animationMatchBy={matchByDataKey('mes')}` para janeiro continuar janeiro na troca de período, além de desenho de linha e respeito a `prefers-reduced-motion` ([Recharts animações](https://recharts.github.io/en-US/guide/animations/)). O custo é de cerca de **150 kB gzip** no pacote inteiro, com Redux Toolkit e immer ([bundlephobia recharts](https://bundlephobia.com/package/recharts@3.10.1)). Ele compensa só se vierem muitos outros gráficos. O Tremor está fora: o peer dele ainda é `react ^18` ([npm @tremor/react](https://registry.npmjs.org/@tremor/react)). Os dados chegam do Server Component como um array serializável de 12 meses (`{ mes: 'YYYY-MM', receita: number }[]`). A troca 6M/12M é estado do cliente sobre esse array, então a metamorfose acontece sem ida ao servidor ([Next Server/Client Components](https://nextjs.org/docs/app/getting-started/server-and-client-components)). O anel de meta (A11) segue a mesma lógica com um `<motion.circle>`, `pathLength` de 0 até o valor e `rotate: -90`, que no Motion gira em torno do centro ([Motion SVG](https://motion.dev/docs/react-svg-animation)).

O cartão que vira ficha (A8) é o caso clássico de `layoutId`. O mesmo id vai no cartão da grade e no contêiner do modal, dentro de `AnimatePresence`. Título e subtítulo levam `layoutId` próprio com `layout="position"`, para se deslocarem sem esticar. O conteúdo que só existe na ficha entra com fade atrasado, e o contêiner fixo leva `layoutRoot` ([Motion layout](https://motion.dev/docs/react-layout-animations)). Se o cartão da grade continuar montado, os dois fazem crossfade. Para um "movimento" puro, o cartão aberto precisa ser escondido. Bordas esticam durante a animação, então o contorno deve ser `box-shadow` ou `outline` via `style`. O Motion não fornece focus trap, Esc nem `aria-modal`. Esses três precisam vir de um `<dialog>` nativo ou de um primitivo como Radix Dialog com `forceMount`, e essa integração não foi verificada. Se a ficha for uma rota (`/quadro/[id]`), o caminho passa a ser um `<ViewTransition name={`ficha-${id}`} share="morph">`, com uma ressalva: se o destino entrar em suspense, nenhum par se forma e o morph não acontece ([Next.js view transitions](https://nextjs.org/docs/app/guides/view-transitions)).

No rapport, a ficha "troca de cor ao avançar a etapa". Aqui a cor significa **situação**, não etapa, então a cor só anima quando a situação muda. O avanço de etapa aparece na barra de progresso. O Motion interpola cores em hex/rgba/hsla e também em **oklch/oklab/color-mix**, que são o formato padrão do Tailwind v4. Ele aceita uma variável CSS como alvo (`animate={{ backgroundColor: "var(--situacao-bg)" }}`) ([Motion animation](https://motion.dev/docs/react-animation)), mas nenhuma fonte confirma como ele interpola uma variável que resolve para oklch. Teste antes de usar ou passe strings `oklch(...)` literais. A barra de etapas anima `scaleX`, que roda no compositor, e não `width`. O `initial={false}` impede que ela anime a partir do zero a cada recarga.

## O arraste nativo não levanta o cartão; o dnd-kit levanta, com custo

O A5 do rapport tem quatro partes: o cartão levanta (escala ~1.04, sombra, leve giro), a coluna de destino ganha contorno, os outros cartões se reacomodam e a cor muda. No HTML5 nativo, a imagem do arraste é um bitmap translúcido gerado pelo navegador, e `setDragImage` "só pode ser usado no handler de `dragstart`" ([MDN setDragImage](https://developer.mozilla.org/en-US/docs/Web/API/DataTransfer/setDragImage)). O Pragmatic DnD, que é um invólucro do nativo, confirma que a prévia é "coletada só no início do arraste" ([Atlassian element adapter](https://atlassian.design/components/pragmatic-drag-and-drop/core-package/adapters/element/about)). No máximo dá para clonar o cartão já girado e escalado, fora da tela, e passar o clone ao `setDragImage`. O resultado é um levantamento **estático**, sem mola, e cada navegador decide se preserva transformações e sombra no bitmap. O resto do A5 funciona no nativo. O destaque da coluna já existe (`sobre`). A reacomodação sai de um `motion.div` com `layoutId={viagem_id}` envolvendo cada cartão, dentro de um `LayoutGroup` que abrange todas as colunas: quando o estado move o cartão de coluna, o React desmonta e remonta o elemento, e o `layoutId` igual anima o trajeto entre as duas posições ([Motion layout](https://motion.dev/docs/react-layout-animations)). O kanban do xNet usa esse padrão, com o Motion num invólucro e o arraste no elemento interno ([xNet PR #681](https://github.com/crs48/xNet/pull/681)).

| Opção | Levanta seguindo o ponteiro | Reacomoda | Toque | Teclado/leitor de tela | Manutenção (out/2026) |
|---|---|---|---|---|---|
| Nativo + Motion (hoje + fase 1) | só snapshot estático | `layoutId` | varia por SO | nenhum, usa o menu "Mover" | — |
| `@dnd-kit/react` 0.5.1 | sim (invólucro interno ou `DragOverlay`) | Motion ou FLIP próprio | pointer, 250 ms | embutido, precisa traduzir | ativa, pré-1.0 |
| `@dnd-kit/core` 6.3.1 | sim | sim | sim | embutido | "legacy", sem release desde dez/2024 |
| `@hello-pangea/dnd` 18.0.1 | sim, pronto | sim | sim | embutido | última release fev/2025 |
| Pragmatic DnD 4.0.0 | não (snapshot nativo) | você implementa | nativo | toolchain | ativa |

A `@dnd-kit/react` 0.5.1 saiu em 15/10/2026, com peer `^18 || ^19`. Os pacotes clássicos agora estão rotulados como "legacy" no site ([npm @dnd-kit/react](https://registry.npmjs.org/@dnd-kit/react); [dndkit legacy](https://dndkit.com/legacy/introduction/installation)). Ela traz `DragOverlay` com `dropAnimation` configurável, sensor de ponteiro com atraso de **250 ms e tolerância de 5 px no toque**, sensor de teclado (Espaço/Enter pega, setas movem, Esc cancela) e anúncios em live region ([dom @0.5.1](https://unpkg.com/@dnd-kit/dom@0.5.1/index.js); [DragOverlay](https://dndkit.com/react/components/drag-overlay)). A armadilha é que ela injeta `transform`, `translate` e `scale` com `!important` no elemento arrastado. Por isso o levantamento precisa ficar num invólucro interno, e nenhum `layout` do Motion pode ir no nó que carrega o `ref`. A propriedade individual `rotate` não está nas regras injetadas, mas isso não foi testado em navegador:

```css
.cartao-corpo { transition: scale .18s, rotate .18s, box-shadow .18s, background-color .3s; }
.cartao-corpo[data-erguido] { scale: 1.04; rotate: -1.5deg; box-shadow: 0 12px 28px rgb(0 0 0 / .18); }
@media (prefers-reduced-motion: reduce) { .cartao-corpo[data-erguido] { scale: 1; rotate: 0deg; } }
```

Como o Quadro só troca de coluna e nunca reordena dentro dela, basta `useDraggable` por cartão e `useDroppable` por coluna, sem `useSortable`. Com isso toda a reacomodação vem do `layoutId` do Motion, e o único nó disputado entre as duas bibliotecas é o cartão arrastado. Para não haver dois pousos, use `dropAnimation={null}` e deixe o `layoutId` pousar o cartão. Ninguém publicou essa combinação, e pode haver um salto de um quadro quando o overlay desmonta. Esse é o critério de aprovação do spike. Os anúncios padrão são em inglês e usam o id cru ("Draggable item a3f9-…"), então precisam ser reescritos com o rótulo da viagem e da coluna. O `<Link>` dentro do cartão conflita com o Enter que pega o cartão, o que pede uma alça dedicada (`handleRef`). O menu "Mover" deve continuar como caminho principal de teclado, porque alguns movimentos exigem o formulário de passagem de qualquer jeito.

A parte do servidor melhora antes de qualquer biblioteca nova. O `useOptimistic` mostra o cartão na coluna nova só enquanto a Transition está pendente. Se a ação falhar, "a Transition termina mesmo assim, e o React renderiza com o `value` atual" ([react.dev useOptimistic](https://react.dev/reference/react/useOptimistic)). Isso substitui o mapa `pendentes` feito à mão e a remoção manual da chave em `executar()`. Com `layoutId` nos cartões, a volta para a coluna antiga vira uma animação de retorno sem código extra. Se a base mudar no meio da ação, como numa recarga realtime, o React reexecuta o reducer com o valor novo. Há duas condições. A Transition só começa **depois** que o diálogo de passagem é confirmado, então cancelar o diálogo não deixa nada para desfazer. E o `await recarregar()` fica dentro da Transition, senão o cartão pisca de volta antes de os dados reais chegarem:

```tsx
function mover(c: Cartao, de: StatusCampo, para: StatusCampo, extra = {}) {
  startTransition(async () => {
    aplicarOtimista({ id: c.viagem_id!, para })
    const r = await moverViagem(c.viagem_id!, de, para, extra).catch(() => ({ ok: false as const, erro: MSG_SEM_REDE }))
    if (!r.ok) { anunciar(`Viagem #${c.numero} voltou para ${rotuloDe(de)}: ${r.erro}`); marcarRecusado(c.viagem_id!); return }
    await recarregar()
  })
}
```

A cor do A5 é o ponto em que o projeto se afasta do template de propósito. No rapport, o cartão assume a cor da coluna ao ser solto. Aqui, ele mantém a cor da situação, e a identidade da etapa fica no cabeçalho e no contorno da coluna. Se o servidor devolver uma situação nova junto com o movimento, por exemplo um atraso resolvido, a cor transiciona ao mesmo tempo que o `layoutId` move o cartão, porque os dois acontecem no mesmo render.

## Vidro só onde há algo atrás para desfocar

O fundo do rapport é um gradiente quente medido em pixel: pêssego `#eddbce` no canto superior, creme `#ece4cd` no centro, sálvia `#e8e6de` nas bordas ([REFERENCIA.md](../REFERENCIA.md)). Ele se monta com três a cinco `radial-gradient()` empilhados sobre uma base. Uma textura de ruído em baixa opacidade quebra o banding: ruído acima de cerca de 0,5 de opacidade "parece estática" ([CSSmatic](https://cssmatic.com/gen-noise-texture.html)), e um PNG ou WebP pequeno repetido custa menos que um `feTurbulence` em tela cheia ([21st.dev](https://21st.dev/blog/react-background-pattern-components)). O fundo deve ficar num `body::before` com `position: fixed`, para ser rasterizado uma vez.

`backdrop-filter` está entre os efeitos CSS mais caros. O custo cresce com a **área** desfocada e com a frequência com que o fundo muda: um painel grande custa mais que seis pequenos, e um cabeçalho sticky desfocado sobre conteúdo rolando é o pior caso comum ([21st.dev](https://21st.dev/blog/liquid-glass-react-components)). Num experimento da equipe do Chrome, até cópias pré-desfocadas animando só a opacidade deram quadros de cerca de **90 ms** na GPU ([Chrome for Developers](https://developer.chrome.com/blog/animated-blur/)). A consequência prática, que é inferência minha, é esta: desfocar um gradiente suave devolve praticamente o mesmo gradiente. Os painéis "Revenue" e "Hot deals" do template parecem vidro, mas sobre esse fundo um preenchimento creme translúcido (`#f4eee4` com alfa) dá o mesmo resultado na tela sem custo de GPU. O blur só aparece de verdade sobre conteúdo com detalhe. Por isso ele fica restrito ao véu do diálogo, ao toast e a uma barra de navegação que role sobre os cartões. As colunas do Quadro, que rolam e recebem atualizações realtime, ficam sem `backdrop-filter`. Também não se aninha vidro dentro de vidro.

O diálogo (A7) usa **um único véu fixo** com blur de 8–12px e um escurecimento leve (`rgb(22 24 24 / .25)`). Só a opacidade do véu anima, nunca o raio do blur, e o diálogo cresce de 0.96 para 1. Na escala padrão do Tailwind v4, `backdrop-blur-sm` é 8px e `md` é 12px ([Tailwind theme](https://tailwindcss.com/docs/theme)). A regra de lint `no-large-animated-blur` sugere ficar abaixo de 10px quando o blur é animado ([React Doctor](https://www.react.doctor/docs/rules/react-doctor/no-large-animated-blur)). O mesmo tratamento serve para o diálogo de passagem que já existe.

Nos cartões sólidos, o contraste decide a cor do texto antes da estética. Pelo cálculo de luminância WCAG 2.x das notas: **mostarda `#e7c14b` exige texto escuro**, com `#161818` a 10,30:1, enquanto branco dá 1,73:1 e reprova até em texto grande. Floresta `#2c5a4d` pede branco (7,85:1). Ferrugem `#c4411d` pede branco (5,10:1, AA), e com texto quase preto passa só em texto grande (3,50:1). Quase preto `#161818` com branco dá 17,8:1. Como a cor representa situação, a cor do texto precisa trocar junto com o fundo, e os dois animam juntos. `prefers-reduced-transparency` só existe no Chromium 118+ (74% do uso global; Safari e Firefox não sinalizam) ([caniuse](https://caniuse.com/mdn-css_at-rules_media_prefers-reduced-transparency)). Ele vale como refinamento com um `@custom-variant`, subindo o preenchimento para 90–95%, mas o design padrão precisa ser legível sem depender do blur.

## Desfazer é uma segunda jogada que o servidor pode recusar

Para o toast (A6), a recomendação é o **Sonner 2.0.8**: 9,4 kB gzip, peer React 19, `position="bottom-center"`, `action: { label, onClick }`, `unstyled` com `classNames` para Tailwind e uma live region `aria-live="polite"` embutida ([npm sonner](https://registry.npmjs.org/sonner); [Sonner toast](https://sonner.emilkowal.ski/toast); [código-fonte](https://github.com/emilkowalski/sonner/blob/main/src/index.tsx)). A entrada do Sonner é em CSS e não usa mola. A pílula feita com Motion e `AnimatePresence` dá a mola por quase 0 kB a mais, mas aí o timer, a pausa ao passar o mouse, o foco no botão Desfazer e o empilhamento ficam por conta do projeto. Num quadro onde vários movimentos acontecem em sequência, o empilhamento pronto vale mais que a mola. O botão mostarda do template entra por `classNames.actionButton`, e `containerAriaLabel="Notificações"` traduz o rótulo da região.

O desenho do Desfazer depende do servidor. Atrasar o commit por 6 s e cancelar no Desfazer esconde o movimento dos outros operadores durante essa janela e perde o movimento se a aba cair. Isso contraria um quadro realtime. A alternativa é **gravar na hora e desfazer com uma ação compensatória** ([tianpan.co](https://tianpan.co/blog/2026-04-27-agent-undo-saga-multi-tool-rollback)). As fontes dessa comparação são blogs de baixa autoridade, e nenhuma diretriz de UX primária foi consultada. A compensação precisa de uma guarda de compare-and-set: só volta se a viagem ainda estiver no status que aquele movimento gravou, para não sobrescrever o movimento de outro operador. A RPC que valida movimentos acrescenta duas consequências que as notas não cobrem e que vêm deste projeto. A volta passa pela mesma validação e pode ser recusada, então o Desfazer precisa tratar a recusa com o mesmo toast de erro. E movimentos que abriram o formulário de passagem, ou que disparam efeitos externos, não devem oferecer Desfazer.

## prefers-reduced-motion precisa de três interruptores

Nenhum dos três motores respeita a preferência do sistema pelos outros. O `<MotionConfig reducedMotion="user">` na raiz do cliente desliga **só transformações e layout**: opacidade e cores continuam animando ([Motion acessibilidade](https://motion.dev/docs/react-accessibility)). A pílula passa a pular direto, e o cartão→ficha e a reacomodação viram cortes secos. O `filter: blur` e a mola do contador não são transformações, então precisam de um `useReducedMotion()` explícito, que troca `spring.set` por `spring.jump` e remove o blur das variants. As view transitions e os keyframes CSS ignoram o `MotionConfig`. Por isso o React recomenda "sempre usar a media query `@media (prefers-reduced-motion)`" ([react.dev ViewTransition](https://react.dev/reference/react/ViewTransition)). O guia do Next indica manter crossfades curtos e remover deslocamentos, já que slides direcionais são "o gatilho mais comum" de desconforto ([Next.js view transitions](https://nextjs.org/docs/app/guides/view-transitions)). O dnd-kit já zera as durações sozinho sob a media query ([sortable @0.5.1](https://unpkg.com/@dnd-kit/dom@0.5.1/sortable.js)). O xNet chegou à mesma conclusão por outro caminho: uma regra CSS global de movimento reduzido não alcança os transforms inline do Motion ([xNet PR #681](https://github.com/crs48/xNet/pull/681)).

## Conclusão

O rapport parece um único sistema de animação, mas em React 19.3 ele se decompõe em ferramentas especializadas. A escolha que mais protege o projeto é negativa: não usar o Motion para transição de rota, não usar `backdrop-filter` onde não há conteúdo atrás e não trocar a cor do cartão pela coluna. Cada uma dessas renúncias corta um custo que o template esconde: o hack de internals do Next, quadros de 90 ms na GPU de notebooks fracos, e cartões que deixariam de comunicar a situação.

O Quadro concentra o único risco técnico real, e ele fica isolado. A fase 1 (`useOptimistic` + `layoutId` + toast) não acrescenta nenhuma dependência ao caminho do arraste e já entrega a volta animada quando o servidor recusa, que é o momento em que a animação mais informa o operador. O levantamento que segue o ponteiro é o efeito mais vistoso e o menos informativo. Ele pode esperar a `@dnd-kit/react` amadurecer, ou ser aprovado num spike com critério objetivo: nenhum salto de quadro no pouso e o toque funcionando em Android e iOS.

| Toast | `sonner` | 2.0.8 | `unstyled` + `classNames`, `bottom-center` |
| Arraste | nativo (fase 1) → `@dnd-kit/react` (fase 2, spike) | 0.5.1 exata, sem `^` | `useDraggable`/`useDroppable`, sem sortable |
| Estilo | Tailwind v4 `@theme` + CSS | — | tokens medidos, `@keyframes surgir`, fundo fixo, `@custom-variant` para transparência reduzida |

1. Instalar `motion@^14.6`, criar `providers.tsx` com `<MotionConfig reducedMotion="user">` e checar se o React Compiler está ligado. Se travar no Windows, apagar `.next`, `node_modules` e o cache do npm.
